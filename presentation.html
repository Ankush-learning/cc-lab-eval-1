Build, Deploy & Analyze a Containerized Microservice Application

Student Management & Course Enrollment System

Architecture: Client → enrollment-service → student-service / course-service

Checkpoints Completed: 1, 2, 3, 4 & 5 (Full Evaluation)

Checkpoint 1
System Architecture & Service Responsibilities
student-service

Port: 3001

Manages student records and profile queries.

  • GET /students
  • GET /students/:id
  • POST /students
  • GET /health
course-service

Port: 3002

Manages course catalog and credit metadata.

  • GET /courses
  • GET /courses/:id
  • POST /courses
  • GET /health
enrollment-service

Port: 3003

Orchestrates inter-service validation flow.

  • POST /enroll
  • GET /enrollments
  • GET /enrollments/:id
  • GET /health
Checkpoint 2 & 3
Dockerization & Inter-Service Networking
Container Architecture
  • Lightweight Node.js 20 Alpine Linux base images.
  • Isolated network: microservice-network (bridge mode).
  • DNS resolution via container names: http://student-service:3001 and http://course-service:3002.
  • Declarative orchestration using docker-compose.yml.
End-to-End Request Flow
  1. Client sends POST /enroll with { studentId: 1, courseId: 101 }.
  2. enrollment-service fetches student details from student-service:3001.
  3. enrollment-service fetches course details from course-service:3002.
  4. Response aggregated & returned with status 201 Created.

Checkpoint 5
Performance Analysis & Key Findings
1. Latency Scaling

Response time increases from 18.4ms (W1) to 112.6ms (W5). Queueing delays emerge as concurrent HTTP connection requests contend for socket handles.

2. Throughput Saturation

Throughput scales linearly up to W3 (125.78 req/s), peaks at W4 (147.60 req/s), and plateaus at W5 due to single-threaded Node.js event-loop CPU limits.

3. Resource Bottleneck

enrollment-service is the primary resource consumer (up to 63.8% CPU, 68.4MB RAM) because it orchestrates multiple downstream fetches.
